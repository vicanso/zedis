# Zedis — Full Feature Tour

Zedis detects what a value is and formats it on the fly. This page is the exhaustive reference — the whole feature matrix first, then each area in detail. The [README](../README.md) has the short version; running the web version is in the [self-hosting guide](./WEB.md), and the Redis / Valkey differences in [Redis and Valkey](./REDIS_VALKEY.md).

## 🚀 Native & Fast

### Native GPU Rendering
**Everything is drawn on the GPU, and the key list is virtual-scrolled over `SCAN` — millions of keys at 60+ FPS with minimal RAM.**

Virtual scrolling combined with `SCAN` iteration keeps the interface responsive no matter how large the keyspace — zero-lag scrolling, instant tab switches, minimal memory footprint.

### Cross-Platform & Appearance
**Native on macOS, Windows, and Linux — Light / Dark / System plus six bundled colour themes, and 8 UI languages.**

A truly native feel across all three desktop platforms. Beyond Light / Dark / Follow-system, the title-bar **Theme** menu carries six bundled palettes — **Ayu · Catppuccin · Flexoki · Gruvbox · Hybrid · Tokyo**. Settings adds a **font size** (12–20 px) and separate **UI** and **monospace** font pickers listing every installed family (the bundled **JetBrains Mono** is the mono default, so code and tables look identical on every platform). The interface itself ships in **8 languages** — English · 中文 · Русский · 日本語 · Português · Español · Deutsch · Français — switched from the title bar or Settings, applied live without a restart.

## 🧠 Smart Data Viewer

### Auto-Decompression
**Transparently unpacks LZ4, SNAPPY, GZIP, and ZSTD.**

Compressed values are unpacked in place so you read the real payload, not a blob.

### Rich Content Decoding
**JSON/RedisJSON, Protobuf, MessagePack, Unix timestamps, media & hex.**

**JSON & RedisJSON** with pretty-printing, syntax highlighting, and saves that send only the changed fields as a `JSON.MERGE` patch (RFC 7396) — **JSONPath** (`$.user.email`, `$.items[?(@.price > 100)]`) works on plain string keys too, no module needed. **MessagePack** deserializes with zero config, and **Protobuf** decodes against `.proto` schemas you register (matched to keys by exact / prefix / suffix / regex, per server); 10/13-digit **Unix timestamps** preview as local + UTC; **images** (`PNG/JPG/WEBP/SVG/GIF`) and a fully editable **hex** view round it out.

### Custom Script Viewer
**Pipe any value through an external shell command for custom decoding.**

Configure a command template with placeholders (`{KEY}`, `{VALUE}`, `{HEX}`, `{HEX_FILE}`, `{RAW_FILE}`); Zedis runs it via `sh -c` / `cmd /c` and shows stdout as the formatted value. **Starter template chips** fill the field with a working command for common tools (each needs that tool on `PATH`). Per-server key matching by exact / prefix / suffix / regex. The key and value reach the command as environment variables and are never spliced into the command line, so a hostile key name cannot turn into a shell command.

### Decode Pipeline
**A documented, deterministic order — your custom viewers always win.**

Every string value goes through the same pipeline, top priority first:

1. **Protobuf viewer** — a registered `.proto` schema matching this key
2. **Custom script viewer** — a configured script matching this key
3. **Native format detection** — MessagePack · GZIP · ZSTD · Snappy · Unix timestamp · images (`PNG/JPG/WEBP/SVG/GIF`) · **Java serialization** (`AC ED 00 05`, with `HashMap` / `ArrayList` / boxed values read into plain JSON) · **Python pickle** (protocol 2+) · **BSON** (extended-JSON spelling for ObjectId, dates, binary)
4. **LZ4** (size-prepended) for non-UTF-8 payloads
5. **Text encodings** on a UTF-8 value that is not JSON — **JWT** (header, payload, `exp` / `iat` / `nbf` as dates; the signature is shown, not verified) · **PHP `serialize()`** · **URL / form encoding** (form pairs as an object) · **Base64** (only when it decodes to readable text, JSON, or a format from step 3 — a token that decodes to noise stays text)
6. **Text / pretty-printed JSON** fallback

Every decoder is also its own detector: a decode has to read the whole value and end where the format says it ends, so a string that merely resembles one (a hex digest inside the Base64 alphabet, `i:1;`) is left alone. All decoded views are read-only — edit the bytes in the hex view. A viewer that matches but fails to decode falls through to native handling, so a bad script never blanks the value. Manual overrides: the **hex** view always shows the raw bytes, and small opaque strings offer a **bitmap** toggle.

## 🗂️ Type & Module Viewers

### Collection Editors
**Hash, List, Set and Sorted Set open as paginated, editable tables — never one blocking `HGETALL`.**

Every collection is walked incrementally (`HSCAN` / `SSCAN` / `ZSCAN`, `LRANGE` windows) with infinite scroll and a loaded/total counter, so a hash with a million fields opens as fast as one with ten. A keyword filter narrows the table — server-side through the scan's `MATCH` for hash / set / sorted set, client-side over the loaded window for lists. Rows are edited in a resizable side panel — add, update, delete — with per-field **Hash TTL** columns where the server supports them and an `RPUSH` / `LPUSH` choice for lists. Sorted sets are read in score order (`ZRANGE` / `ZREVRANGE`) with a toolbar toggle for ascending vs descending. **Bulk add** takes pasted TSV/CSV (one row per line), and the visible table exports to CSV/JSON. Elements **decode like string values** — MessagePack, gzip, a JWT (an image is named rather than drawn) — so a table of packed blobs reads as text, while every write and delete still sends the **stored bytes**; an element that is neither text nor a known format is edited as hex. A JSON element gets the string editor's **Text / Tree** switch above the form — tree operations rewrite the form's text, and Save writes them — and a MessagePack or gzip element that decodes to JSON gets the same tree, read-only. Rows **multi-select** for a batch delete, and the toolbar runs the type's own operations (`LTRIM` / `LPOP` / `ZINCRBY` / `ZPOPMIN` / `HINCRBY`) instead of a read-modify-write round trip. Sorted sets add a **score-range filter** (`ZRANGEBYSCORE`) on top of the ordering.

### Specialized Type Viewers
**Opaque values open in purpose-built, interactive viewers.**

**Bitmap/Bitfield** paints bits on a GPU grid (`SETBIT`/`BITCOUNT`/`BITFIELD`), where a click flips a bit only once *Edit bits* is switched on; **HyperLogLog** shows `PFCOUNT` cardinality; **Vector Set + KNN** (Redis 8) walks the HNSW graph via `VSIM`, narrows it with a `FILTER` expression over element attributes (neighbours show theirs inline via `WITHATTRIBS` on 8.2+, `FILTER-EF` sets the candidate budget) and shows the queried element's dequantized `VEMB` components, copyable; **Geo Map** plots a sorted set's members (`GEOPOS`) on a tile-less, zoom/pan radar, with a `GEOSEARCH` radius filter and Shift-click distance measuring; **Probabilistic** (RedisBloom: Bloom/Cuckoo/Count-Min/Top-K/t-digest) and **Time Series** (RedisTimeSeries `TS.INFO` + bucketed `TS.RANGE` chart) each get a dedicated card. Which viewer opens depends on the key's type / module. A module type Zedis has no viewer for (RedisGraph, Tair, …) is not a dead end: the editor names the type and the server's loaded modules, shows the value as its serialized `DUMP` bytes read-only — behind the same auto-load cap as strings, and never above a 32 MB hard cap, since `DUMP` serializes the whole value on the server's main thread — and keeps rename / TTL / delete / copy working; the key tree's type filter lists such types by name. These viewers **write**, not only read: Bitmap flips bits and combines keys (`BITOP`), HyperLogLog merges (`PFMERGE`), Geo adds members and measures between them (`GEOADD` / `GEODIST`, radius *and* box search), and Time Series has `TS.ADD` / `TS.ALTER` with compaction rules plus a multi-series **`TS.MRANGE` explorer** that charts several series picked by label.

### Module Browsers
**Dedicated panels for RediSearch (FT.*) and Functions (Lua libraries).**

**RediSearch**: list/inspect indexes, run `FT.SEARCH` / `FT.AGGREGATE` with chips, create / alter / drop from a form. A query's `$name` placeholders get a **PARAMS editor** row each — TEXT, or a vector kind (FLOAT32 / FLOAT64 / FLOAT16 / BFLOAT16) that turns comma-separated floats into the little-endian blob a `KNN` / `VECTOR_RANGE` clause expects — and the bindings travel with `FT.EXPLAIN` / `FT.PROFILE` too. **Functions** (Redis 7+): manage libraries via `FUNCTION LIST/LOAD/DELETE` with a tree-sitter Lua editor, starter templates, direct **`FCALL`** invocation, and `DUMP` / `RESTORE` / `FLUSH` / `STATS` / `KILL`. A RediSearch index also reports the **space it occupies**, a TAG field lists the values it has indexed (`FT.TAGVALS`), and a query offers **spelling suggestions** for terms that matched nothing (`FT.SPELLCHECK`). Both auto-hide when the module / version isn't present.

### Redis Streams
**Browse, live-tail, and manage consumer groups without leaving the GUI.**

Browse entries, **live-tail** new messages (`XREAD BLOCK`, ring-buffered), inspect Consumer Groups & Pending Entries via `XINFO`, and manage groups (`XGROUP CREATE` / `SETID` / `DESTROY`, with a confirm guard on destroy). On Redis 8.2+ a pending row also offers **ack + delete** in one atomic `XACKDEL`, and the trim dialog gains the **reference policy** (KEEPREF / DELREF / ACKED — what happens to groups' pending references of trimmed entries); on 8.6+ the info view shows the **idempotent producer (IDMP)** counters — producers tracked, entries added, duplicates suppressed. On 8.8+ a pending row can also be **released** without an ack (`XNACK FAIL`: consumer cleared, delivery count kept, claimable at once), and each group row offers **create consumer** (`XGROUP CREATECONSUMER`, 6.2+).

### Pub/Sub
**Subscribe to channels and publish messages, with a live message log.**

Open it from the status-bar **Tools** menu or the **⌘K** command palette (same entry as the other server tools). Pattern-based subscriptions (`PSUBSCRIBE`), a `PUBLISH` composer, and incoming messages streamed into a ring-buffered `(time, channel, message)` table — Redis's other messaging primitive alongside Streams. A **Sharded** toggle (Redis 7+) switches to `SSUBSCRIBE` / `SPUBLISH` — on clusters messages are routed by the channel's hash slot instead of broadcast to every node, over a dedicated RESP3 push connection that survives failovers.

## 📊 Real-Time Observability

A built-in, GPU-accelerated dashboard for monitoring your instances.

### Live Metrics
**Real-time charts for CPU, memory, latency, clients, throughput and evictions — with 7 days of history.**

Eight headline stat cards (memory · clients · OPS · latency · hit rate · net in / out · evicted keys) sit above GPU-accelerated time-series charts for CPU usage, memory usage, latency, connected clients, total commands processed, output KB/s, key hit rate and evictions. Samples are also persisted locally (one per minute, kept for 7 days), so the **Live / 1h / 24h / 7d** ranges answer "did memory grow overnight?" even across app restarts. The history **exports to CSV**, and network throughput is charted alongside the client count, so a traffic spike can be read against the connections behind it.

An **Alerts** dialog on the same page (or the **Threshold Alerts** checkbox on the server's Safety tab) turns on **opt-in per-server threshold alerts** — off by default, so no rule runs until you enable it for that server. Eight rules cover memory usage (% of `maxmemory`), blocked clients, connected clients, ping latency, eviction rate, replication lag, instantaneous ops/s and link offline, each with its own threshold, sustained duration and cooldown, plus a recent-alerts log.

### Memory Analyzer + Recommendations
**Hunt BigKeys, see the TTL distribution, get instant offline health checks plus optional AI tips.**

Sort the Top-N table by **Size / Hottest / Coldest** (`OBJECT FREQ`/`IDLETIME` auto-picked from `maxmemory-policy`), with a **TTL histogram** alongside. On Redis 8+ a **key-size distribution** card reads `INFO keysizes` — exact per-type bucket counts straight from the server (strings by value bytes, containers by element count), no sampling, shown even before a scan runs and summed across cluster masters. The moment a scan finishes, an **offline rule engine** flags issues automatically — big keys, keys that can't be evicted under a `volatile-*` policy, `noeviction`, high fragmentation, many tiny strings that should be a Hash, and memory-dominating prefixes — no config or network needed. One click also sends the report (key *names*, sizes, TTLs only — never values) to any **OpenAI-compatible** endpoint for inline advice in your UI language. The report also breaks the keyspace down by **type and storage encoding** — which encodings dominate and what they cost — names **module types** rather than showing an opaque blob, and lets you **drill into a prefix**: click a namespace to re-run the analysis scoped to it, so a big-key hunt narrows level by level instead of starting over.

Prefer not to touch production at all? **Analyze RDB** parses a local dump file offline — a streaming parser (every value encoding through Redis 8.10 — 8.8 arrays and 8.10 compact hashes included, values length-skipped so multi-GB files parse at I/O speed) feeds the same tables, TTL histogram, and rule engine, with zero commands sent to any server. Sizes are the keys' serialized bytes in the file: not equal to live memory, but a faithful ranking for big-key and prefix hunting. Both the live scan and the file parse show a progress bar, and the prefix / top-key tables export to CSV.

Every run (live or offline RDB) also builds a **Data Dictionary**: variable key segments are collapsed automatically (`user:10042:profile` → `user:{id}:profile`, plus `{uuid}`, `{date}`, `{hash}` and `{token}`), with estimated key count and memory, size percentiles (`p50`/`p95`/`max`), TTL policy (Permanent, Fixed, Range, or Mixed), and — for live scans — best-effort inferred field names and scalar/JSON types (`integer`, `float`, `boolean`, `timestamp`, `uuid`, `json`, `string`, `array`, `object`, `binary`) with zero raw business values ever retained or exported. Inspect the schema in the **Data Dictionary** modal, copy it as Markdown, or export it as Markdown or JSON.

### Performance Diagnostics
**Slow Log ↔ Latency, live MONITOR, clients, and command stats.**

The Performance panel cross-links **Slow Log** entries with `LATENCY` events (±5 s chips jump to the `LATENCY HISTORY` sparkline), aggregates them into a **Top Commands** view ranked by total time consumed (one click filters back to the raw entries), and exports the filtered view to **CSV/JSON** — with a confirm-guarded `SLOWLOG RESET` to start a fresh window; plus live `MONITOR` with keyword filtering, Zedis's own connections left out of the feed unless asked (the heartbeat's `INFO` used to be most of a quiet server's feed), pause, a live events/s badge with an auto-stop rate guard, and CSV/JSON export — and a timed **sample** (5, 10 or 30 s) that ends by itself and counts every command it saw by client, command and key prefix, one click from a row back to its lines; client management (`CLIENT LIST` with user, library, query-buffer and memory columns / `CLIENT KILL`, filterable by connection type — normal / replica / master / monitor / pub-sub / blocked — with a confirm-guarded batch kill of everything matching the filter, a **Kill by filter** form for `CLIENT KILL` by ID / ADDR / LADDR / USER / TYPE / MAXAGE, and `CLIENT PAUSE` (WRITE or ALL, timed) beside `UNPAUSE`); and a per-command **calls/second** table from `INFO commandstats` with a summary row, idle/self-connection noise filtering, and export. One click also pulls the server's own verdicts — **`MEMORY DOCTOR`**, **`MEMORY STATS`** and **`LATENCY DOCTOR`** — rendered as readable reports instead of a wall of raw text. On Valkey 8.1+ the Slow Log panel gains **`COMMANDLOG`**: next to slow commands sit the server's logs of oversized **requests** and oversized **replies**, which is what finds the client shipping a 10 MB argument. Each latency event carries an **average** too — exact since the last reset on Valkey 8.1+, which keeps the sum, and the mean of `LATENCY HISTORY` elsewhere — and on Valkey 8.0+ an `EVALSHA` in the slow log opens the **script behind the digest** (`SCRIPT SHOW`). A `CLIENT PAUSE` in force shows in the status bar as a chip with the time left, and a click unpauses. Valkey 8.1+ reports pauses in `INFO clients`, so the chip appears whoever paused the server; elsewhere it shows only a pause Zedis itself sent.

### Hot Keys
**`HOTKEYS` tracking (Redis 8.6+): which keys burn the CPU and the bandwidth.**

Start a collection (CPU time and/or network bytes, top 10/20/50), watch the two ranked lists fill live, stop, read, reset. Each entry carries its share of the totals as a bar and a percentage, and a click copies the key name. On a cluster the tracking runs on every master at once and the lists merge — slots are disjoint, so nothing double-counts. Start/stop/reset need write access (a read-only connection can still read the report), and on servers without the command the panel shows an explanation instead.

### Value Search
**Find which key *contains* some text (a guarded, sampled scan).**

Redis can't index values, so this `O(keyspace)` search runs behind guardrails: a mandatory key prefix, a cap of 10k keys / 10s by default (Settings → Key Behavior, up to 1M keys / 300s; cancellable), and values over 1 MiB skipped — searching string values, hash fields, and list/set/sorted-set members, all of them or one type (narrowed by the server with `SCAN … TYPE`), with each hit showing where it matched. A search the cap, the clock or the Stop button ended can be **continued** from where it stopped with a fresh budget, keeping its hits — hits past the match cap included. A guide on the empty page and a key filter over the results keep the flow clear; results are an explicit **sample**, never claimed exhaustive.

### Cluster Health & Management
**Topology tree with replication lag, a slot map, per-node load, and a reshard wizard.**

Inspect Cluster/Sentinel topology as a tree (masters, slot ranges, replicas, per-replica lag from `INFO replication`), compare each master's memory, ops/s, keys and clients with its share of the slots on the Load tab — a share well above it, the mark of a big key or a hash tag piling keys onto one slot, is flagged — then act: `CLUSTER FAILOVER` / `FORGET` / `MEET` / `REPLICATE`, and on Sentinel `FAILOVER` / `RESET` / `REMOVE` / `MONITOR` (add a master) / `SET` (quorum, down-after, failover-timeout, parallel-syncs, auth-pass) / `FLUSHCONFIG`, with `CKQUORUM` answered per sentinel — every write goes through the confirm dialog, stricter on Prod. `SENTINEL` commands go to the sentinels themselves (the addresses in the connection plus the peers they report), never to the data master the connection normally talks to, and each master row shows what the sentinels say about it: quorum, sentinel count, timings, down flags. If a connection names no master and its sentinel monitors several, Zedis connects to the first by name, says so, and offers the others in a switcher that updates the saved connection. Three more tabs go deeper: **Slots** maps every master's slot ranges and in-flight migrations plus a **Hot Slots** table (`CLUSTER SLOT-STATS`, Redis 8.2+) — top slots by key count, or by memory / CPU / network I/O on clusters running `cluster-slot-stats-enabled`, each row color-coded to its owning master; **Load** samples memory / OPS / clients across the masters, and the **Reshard** wizard moves slots between masters — pick a target (and optionally a source, one click from a Load card), preview the plan, then run the reshard behind a confirmation, with a live per-slot progress bar. Slots that end up **unassigned or claimed by two nodes** are flagged with a one-click repair, a **rebalance** spreads them evenly again, and on Valkey 9+ and Redis 8.4+ a migration runs as the server's own **atomic slot handoff** (`CLUSTER MIGRATESLOTS` on Valkey, `CLUSTER MIGRATION` on Redis) instead of moving keys one by one. The node list counts the nodes the cluster marks **failed** or **possibly failing** (`fail` / `fail?` in `CLUSTER NODES`), and on Valkey 8.1+ shows each node's **availability zone**.

On a **standalone** server the same page is the **replication view**: the primary and its replicas as `INFO replication` reports them, each replica with its lag — plus the commands that change the topology. `REPLICAOF host port` attaches a replica, `REPLICAOF NO ONE` promotes one, and **`FAILOVER`** hands the primary role over in a coordinated way rather than by force. Sentinel and Cluster connections keep their own failover machinery instead, so the page never offers two ways to do the same thing.

### Persistence & Keyspace Events
**RDB/AOF status with one-click saves, plus live key-event triage.**

A persistence panel reads `INFO persistence` (last save, AOF growth, fork failures) with one-click `BGSAVE` / `BGREWRITEAOF` (confirmed, stricter on Prod) and, on Valkey 8.1+, a **Cancel** for the snapshot in progress (`BGSAVE CANCEL`), per-node status rows on clusters, and a **Policy & paths** card showing the configured `save` rules and AOF settings from `CONFIG GET`. **FLUSHDB / FLUSHALL** sit in the same Tools → Administration group, disabled on a read-only connection and routed through the destructive-command confirm (stricter on Prod), so clearing a dev database no longer means dropping into the CLI. Keyspace notifications parse keyspace/keyevent channels into a filterable `(time, db, key, event, source)` table — "which client just deleted user:42?" — with one-click `notify-keyspace-events` presets, pause, and export.

### Raw INFO Browser
**Every `INFO everything` field in one filterable table.**

The structured panels cover the common fields; this page covers the long tail — `errorstats`, `latencystats` percentiles, fork/COW costs, `sync_full` counters, uptime — without dropping to the terminal. Filter matches section, field, and value; a **Snapshot → Compare** flow shows a field-level diff against an earlier capture (changed / added / removed — field reordering produces no noise); the visible view exports to CSV. On clusters every master is listed with its address in the section column, so filtering one field compares it across nodes. Read-only, and degrades to `INFO all` / plain `INFO` on older servers.

### CONFIG Editor
**A typed `CONFIG GET/SET` editor with inline parameter docs.**

Runtime parameters render with type-aware editors instead of raw strings, grouped by concern (memory & eviction, RDB, AOF, defrag, replication, cluster, network, security, TLS, latency, logging, data-type limits, scripting). The common parameters carry inline help lifted from the official `redis.conf` — what a knob does, right where you change it — in English and Chinese, with English as the fallback for the other UI languages. The `maxmemory-policy` picker includes Redis 8.6's `allkeys-lrm` / `volatile-lrm` (least-recently-modified) when the server supports them. Writes go through `CONFIG SET` behind the confirm dialog, which is stricter on Prod. A `CONFIG SET` only lives until the server restarts, so the panel also offers **`CONFIG REWRITE`** — one guarded click that folds the running configuration back into the server's own config file, and says so plainly when the server was started without one.

### Troubleshooting Report
**Everything the server says about itself, in one paste.**

**Tools → Troubleshooting Report…** reads the server once — who it is, each master's state from `INFO` (memory against its limit, fragmentation, clients, hit rate, evictions, replication, persistence, keyspace), `MEMORY DOCTOR` and `LATENCY DOCTOR` in the server's own words, the latency events, the newest slow-log entries and the settings that explain them — and adds what this session found: the memory analyzer's last scan (its recommendations, top prefixes and keys) and the latest hot-key collection. **Copy** it as Markdown for a ticket or a chat, or **save** it as Markdown or as one HTML file that opens anywhere, light or dark. It holds key names, sizes and settings, never a value: a slow-log entry keeps only its command and first argument, with credentials blanked. A part the server refuses — `CONFIG` or the doctors on a managed cloud — is said in the report with the server's reason; the rest is still there. In the browser the files are downloads.

## 🔑 Keys & Data Management

### Key Organization
**Namespace tree with TTL chips, favorites, and client-side tags & notes.**

Keys group into a nested tree by `:` with compact TTL chips (green live / red expiring; a key that never expires has none). Bookmark keys, revisit search history, and add colour **tags & notes** — stored in a local redb file, **zero Redis cost**, never leaving the machine. Expanding a folder whose only child is another folder opens the whole chain at once, so a deep `app:user:profile:…` namespace costs one click instead of one per level — and a folder you collapse by hand stays collapsed. The split is smarter than a plain `split(':')`: separators inside a cluster **hash tag** (`user:{tenant:42}:profile`), inside a **quoted JSON blob**, or inside an **ISO-8601 timestamp** are not level boundaries, so such keys stay whole instead of shattering into folders named `55` or `44.487892+00`. The separator, tree depth, scan size and TTL-chip visibility are all overridable per server. The tree **sorts** by name, TTL or type (ascending or descending), and a **flat list** toggle drops the folders entirely when a namespace is more noise than structure. The keyword filter takes a **regular expression** as well as a substring, and **Shift-click** selects a whole range of rows for the batch operations below.

### Key Editing & History
**Rename, per-field TTL, file import/export, bulk paste, and version history.**

Atomic **rename** (`RENAMENX`, overwrite-guarded), per-field **Hash TTL** (`HEXPIRE`/`HPERSIST`, Redis 7.4+ / Valkey 9.0+ — in the edit panel, or set and removed alone from a row's right-click menu; on 8.0+ a field write and its TTL go out as one `HSETEX`, and editing a value keeps its TTL via `KEEPTTL`), **value file export/import** (binary-safe, `KEEPTTL`), **bulk paste** of TSV/CSV into Hash/List/Set/ZSet, and a client-side **last-10-versions** write history with diff & one-click restore — side by side or unified (the layout last used is kept), with the words that changed within a line marked; large values are compared line by line too, unchanged stretches fold away, and the diff steps from one change to the next. Deleting a key — one, or a multi-selection of up to 100 — first stashes its `DUMP` payload into a **local recycle bin** (24h, restorable from Tools → Keys & Data → Recycle Bin, TTL preserved; opt-out in Settings — a folder delete or a flush is never stashed) — a fat-finger delete on production is no longer final. Oversized String/JSON values are never loaded blindly: the editor shows the size and fetches only on an explicit **Load anyway**. On Redis 8.4+ / Valkey 8.1+ a string save is a **compare-and-set** (`SET … IFEQ` against the bytes you loaded): a concurrent writer's change is never silently clobbered — the refused save reloads the winner's value and asks before overwriting. The key bar shows the value's **storage encoding** and its **idle time**, and a TTL can be set as an **absolute moment** (`EXPIREAT`) from a date picker instead of a number of seconds, or dropped with **Remove TTL** (`PERSIST`). The value editor has **find & replace**; a string holding JSON opens as a **JSON tree** with path-level operations (`JSON.SET` / `JSON.DEL` / `JSON.NUMINCRBY` / `JSON.TOGGLE` / `JSON.ARRAPPEND` / `JSON.STRAPPEND` / `JSON.CLEAR` — applied locally when the key is a plain string rather than a RedisJSON document) — whether a JSON value, or a JSON element of a hash, list, set or sorted set, opens as its text or as the tree is a choice in *Settings → Key Behavior* — and every save is **checked, and can be formatted or minified** first. A per-session **change log** records what you altered, with a structured diff for collections.

### Bulk Key Operations
**Multi-select delete, batch TTL, DUMP/RESTORE import/export, auto-refresh.**

Multi-select to delete dozens of keys at once; set / remove TTL across a whole selection or prefix — or on one key, from its right-click menu — (cluster-safe, with a confirmation that is stricter on Prod; on Redis 7.0+ / Valkey the batch takes an `EXPIRE` condition — NX / XX / GT / LT — and reports how many keys the server left unchanged). **Export** is available from the tree selection *or* the status-bar **Tools → Keys & Data → Export Loaded Keys…** entry (current SCAN subset for this connection/db — not a keys-only name list). The export window picks **binary DUMP** (full-fidelity, streams through `RESTORE`) or **readable JSON / CSV** (full values + TTLs, for people and downstream tools, and for editing by hand and importing back), and an optional **key-prefix filter** with a live matched/total count narrows the job before it starts. **Imports accept all three formats**, sniffed from file content rather than the extension: the binary bundle streams through `RESTORE`, while JSON/CSV files are parsed up front (a typo from hand-editing fails with a message naming the key before anything is written) and written back with type-native commands, TTLs restored — entries the export marked `truncated` are refused rather than silently importing partial data. Auto-refresh keeps the tree current on fast-changing instances.

### Cross-Server Tools
**Copy or diff a key, or diff full configs, between two servers.**

**Copy** a key with value + TTL (`DUMP`/`RESTORE`), **diff** a string key against the same key elsewhere (side-by-side), or **diff** two servers' `CONFIG GET *` (striped table of only what differs). Built for "why does prod differ from staging?". A whole **prefix** can be copied too: pick the keys by pattern and Zedis streams them straight through `DUMP` / `RESTORE` to the other server, TTLs preserved, with a per-key result list. A copy between a Redis and a Valkey — one key or a prefix — works as well: the two use different RDB version numbers for their `DUMP` payloads, so `RESTORE` refuses them in every direction but Valkey 8 → Redis, and Zedis then **re-creates the key by type** from the source (string, hash, list, set, sorted set, stream with its entry ids, JSON — TTL included), with the log saying which keys were copied that way; module types, consumer groups and per-field TTLs cannot be copied this way and are named as lost. A single key asks the target first, writing nothing: if it would be re-created, the confirm lists what would not travel ("its 2 consumer group(s), with their pending entries", "the TTLs of 3 field(s)") before anything is copied, a module type is refused up front, and the result says it was re-created by type. And two **databases** can be compared over a prefix — in both, only here, only there, or present in both with different values — so a migration is verified rather than assumed.

## 🔐 Security & Privacy

### Privacy-First
**Your data and credentials stay on your machine; the only request you didn't ask for is the update check.**

Tags, notes, favorites and search history live in a **local redb file** — zero Redis cost, never sent anywhere. Connection secrets are **encrypted at rest**, and sharing a connection as JSON **strips credentials** by default. The optional AI analysis sends only key **names, sizes and TTLs — never your values**, and only to the OpenAI-compatible endpoint *you* configure. The custom script viewer runs locally through your own shell. **No telemetry, no accounts, no cloud.** The one unprompted request Zedis makes is the **startup update check** — at most once every two days, carrying nothing but the app version, sent to GitHub and, when GitHub cannot be reached, to the Gitee mirror instead, and switchable off in Settings (see *Staying Current* below).

### Connection Safety
**Environment tags + confirm dialogs that get stricter on production.**

Tag each server with a preset environment — **Dev / UAT / Prod** — shown as a colored chip in the sidebar and status bar; the title bar also shows the active **db** and a quiet **Prod** badge when the connection is high-risk. The status-bar **DB dropdown** lists each database with its **key count** (from `INFO keyspace`) so you can pick a non-empty db at a glance, and each server can **pin the database it opens on** (leave it empty to reopen the last one used). Lock any connection **read-only** — globally in its settings, or just for the current session from the status bar. A **Prod** server starts with its writes **locked** (any server can, via the *Writes* choice on its Safety tab): the status-bar lock asks for the server's name and opens a **15-minute window**, shows what is left, and locks again by itself — in the web version its server (the bridge) enforces the same window, so a script that calls it directly gets no further than the page. In the browser a Lua script or function call (`EVAL` / `EVALSHA` / `FCALL`, not the `_RO` forms) sent to a locked or **Prod** server is confirmed every time, inside the window too, and by typing the server's name on **Prod**: Zedis cannot tell from the command what a script will write. Destructive actions (`FLUSHALL` / `FLUSHDB`, `CONFIG SET` / `REWRITE` / `RESETSTAT`, `SHUTDOWN`, `DEBUG`, `SCRIPT FLUSH`, `FUNCTION FLUSH` / `DELETE`, `SWAPDB`, `KEYS *`, a `DEL` of 50+ keys, key/server delete, `XGROUP DESTROY`, cluster ops…) are intercepted with a confirm dialog that escalates its wording on a **Prod** server. A per-server **Confirm Writes** switch widens that net to *every* write command typed into the terminal, on connections where nothing should happen by accident.

### ACL Management (Redis 6+)
**GUI for the full ACL lifecycle.**

List users, view flags / commands / key patterns / channel rules, and edit via quick presets (Full / Read-only / Disabled) plus toggleable chips for command categories and wildcards. ACL v2 **selectors** (Redis 7.0+) — the additional `( … )` permission groups — are shown per group in the exact SETUSER syntax and round-trip through the rules editor losslessly: the emitted text leads with `clearselectors`, because a bare `( … )` *appends* server-side and would silently duplicate every selector on each save. Beyond editing, the panel reads the server's **security log** (`ACL LOG`) — who was denied what, and when — which is where a failing client's missing permission actually shows up. A **dry-run tester** (`ACL DRYRUN`) answers "could this user run this command on this key?" without running it, **`ACL GENPASS`** mints a strong password, and the whole user set **saves to / loads from the server's aclfile** (`ACL SAVE` / `ACL LOAD`) so the rules survive a restart.

### Secure Connections & Groups
**TLS/SSL and SSH tunnels, with named, shareable server groups.**

Full **TLS/SSL** — custom CA, client certs as pasted PEM *or* file paths, an encrypted PKCS#8 client key with its passphrase, and a **TLS server name** for endpoints reached by IP or through a tunnel whose certificate names something else — and **SSH tunneling** with password, private key or agent (the OpenSSH agent pipe on Windows too). Blank SSH fields take `HostName`, `User`, `Port`, `IdentityFile` and `ProxyJump` from **`~/.ssh/config`** exactly as `ssh` does, a **jump host** can also be set on the form (one hop), and a host key seen for the first time is **confirmed by fingerprint** before it is trusted — known_hosts and Zedis's own record are read, never rewritten. A Sentinel connection can list **several seed addresses** and carry the **sentinels' own username / password** when they differ from the data nodes' (the Redis Insight, ARDM and Tiny RDM importers keep both sets apart); a cluster can **read from replicas**; a **Unix socket path** in the host field connects locally; hosts and SSH addresses accept **IPv6 literals**, bracketed or bare. When a connection fails, the server form's **Diagnose** button runs staged diagnostics — DNS → TCP → SSH auth → SSH tunnel → TLS → AUTH → PING — pinpointing the failing layer with a targeted fix hint instead of one opaque error. Organize connections into named, collapsible **groups** and reorder them. **Right-click a connection in the sidebar** for its menu: open it here or in a new tab, edit, clone or diagnose it, move it to another group, disconnect or reconnect every tab on it, or delete it. Export any selection of connections as JSON (credentials stripped by default) — or set a passphrase to emit a compact, portable **share token** (`ZEDIS1.…`, Argon2id + AES-256-GCM) that only opens with that passphrase; the import dialog detects the token and prompts for it. Migrate in by pasting a `redis://` (or `valkey://`) URI, a **Redis Insight** database export, an **Another Redis Desktop Manager** export (`connections.ano`), or a **Tiny RDM** `connections.yaml` (the file inside its exported zip) — every connection lands at once, with groups, TLS and SSH settings mapped over. Those clients store secrets in the clear; once imported they live in Zedis's per-machine encrypted store.

### Link Health & Failover
**A 2-second heartbeat shows the connection's real state — and a dropped connection recovers on its own.**

Every connection is checked on a 2-second heartbeat; the status-bar dot reads **Connected / Reconnecting / Offline** (offline only after repeated failures, so one slow round-trip doesn't cry wolf), and the dot itself is the disconnect / reconnect button. Server-state replies — a dropped link, `LOADING`, `BUSY`, `READONLY`, `MASTERDOWN`, `CLUSTERDOWN` — are folded into **one throttled, localized notice** instead of a wall of raw errors, and the stale connection is dropped so the next call opens a new one: on Sentinel and Cluster that re-runs discovery, so **after a failover Zedis reconnects to the new master by itself**. When the heartbeat recovers, the selected key is reloaded and the panels refresh — you get "Connection restored", not a screen of stale data. A replica connection is labelled as such, since writes there come back `READONLY`.

## 🔀 Redis and Valkey

### Both Fully Supported
**Which features are available is decided for Redis and for Valkey separately, each by its own version; the Valkey-only features have panels of their own.**

Valkey forked from Redis 7.2.4 and numbers its releases on a track of its own, so a version check written for Redis would send a Valkey server commands it never shipped, or hold back ones it shipped earlier. Zedis instead checks every version-dependent feature against Redis's and Valkey's own versions separately, and the Valkey-only features have their panels and actions: the `COMMANDLOG` large-request / large-reply logs, atomic slot migration, multiple databases in cluster mode, `SCRIPT SHOW`, availability zones, `BGSAVE CANCEL` and server-reported client pauses. The module browsers take valkey-json, valkey-search and valkey-bloom as they are, and report the `FT.*` commands valkey-search lacks as unavailable rather than failing. A setting that would crash a server is withheld: Redis 8.0–8.2.6 and Valkey 8.0 crash when a `CLIENT NO-TOUCH` client unblocks another, so Zedis does not set that flag there. A copy between the two re-creates a key where `RESTORE` refuses the other flavor's payload (see *Cross-Server Tools*). The live integration suite runs on Redis 6.2 / 7.2 / 8.0, Valkey 8.0 / 9.0, `redis-stack` and `valkey-bundle` on every change. The [Redis and Valkey](./REDIS_VALKEY.md) page lists every divergence with the version on each side.

## 🧭 Limited & Non-Standard Servers

### Capability Probe
**Panels and buttons grey out *with the reason* instead of failing.**

Proxies (Twemproxy / Codis / Envoy) answer `unknown command` outside their whitelist, managed clouds (ElastiCache / Azure Cache / Tair) rename or ACL-deny the administrative ones, and Redis-compatible servers (Valkey / Dragonfly / KeyDB / Kvrocks / Garnet) ship different subsets. Rather than a hand-maintained table per brand, Zedis **probes** the server once right after connecting, to see which commands it accepts — in the background, on a dedicated connection, with read-only commands only (mutating commands are checked through `COMMAND INFO` + `ACL DRYRUN`, never executed) — and caches the result per server.

The rest of the UI works from that result. A panel that cannot work without a missing command shows an explanation in its place; a button whose command is unusable is disabled with a suffix naming it (`CONFIG GET · not supported by this server`, `SLOWLOG GET · denied for this user (NOPERM)`). The **Tools** menu is the exception: a panel the server does not have (a module not loaded, a version too old for it, a command it answers `unknown command` to) is left out of it rather than greyed, since nothing the user can do changes that, while one this user is *denied* stays in, disabled with the reason. The key editor keeps working on a server without `SCAN` — type an exact key name and press Enter, and recent keys (**⌘P**) still work. A `NOPERM` / `unknown command` reply at run time updates the same result: one localized notice, then the UI quietly degrades instead of repeating the error.

**Tools → Server capabilities** shows the full matrix — every probed command with its verdict — plus a **Re-probe** button for when an administrator has just granted you the permission.

## 🌐 Web Version (Self-Hosted)

### The Same App in a Browser Tab
**Compiled to WebAssembly and served by one small Docker image — host it once and the whole team reaches your Redis from a tab, with nothing to install.**

A browser cannot open a TCP socket, so the page never talks to Redis directly: a small HTTP server — **`zedis-bridge`** — serves the WebAssembly bundle and forwards RESP frames on the browser's behalf. That forwarding is the whole protocol, so a panel built for the desktop works in the browser as it is, instead of waiting for an endpoint of its own. The image is `vicanso/zedis-web` (linux/amd64 and linux/arm64, ~26 MB); its `/data` volume holds the server list — secrets encrypted at rest with the `master.key` beside it — and the saved logins, so a restart signs nobody out. When the host name is not Zedis's alone, `ZEDIS_BRIDGE_BASE_PATH` moves the page, its files and the API under a path of their own, with the login cookie scoped to it so the neighbouring applications never receive it. The [self-hosting guide](./WEB.md) has the `docker run` lines and a reverse-proxy example.

### Accounts & Ownership
**Sign-in is required, a server entry is private until you share it, Redis passwords never reach the browser, and an audit log can record who did what.**

Accounts are **registered on the bridge**, never configured: the first is the administrator, made on the page with a one-time setup token from the bridge's log, and everyone after it registers through an invitation link the administrator makes on the account page (**Account…** in the title-bar menu) — with a role, the shared servers it sees and an expiry — or, where the operator turns it on (`--signup approval`), asks on the sign-in page and waits for an administrator to approve the request with a role and servers. Passwords are kept as Argon2id hashes, failed attempts are throttled per address, a forgotten password is a reset link, the last administrator cannot be removed, and `zedis-bridge setup-token` on the host makes a new administrator when every one is lost; accounts from the old `ZEDIS_BRIDGE_USERS` / `--users-file` are imported once. The page asks for a username and password; scripts use HTTP Basic against the same accounts. An account may be **read-only**: it looks at everything it can see and changes none of it. An account many people share — a demonstration's — may also be **locked**: it cannot change its own password or MCP tokens, and keeps no favorites, history or preferences on the bridge, so no visitor changes what the next one finds. The bridge itself refuses a write with a `403`, rather than leaving that to the page, and it judges by an allowlist of reads — so `EVAL`, `BITFIELD`, `GETDEL` and every unrecognised module command are refused, and no confirmation gets past it. A **server entry belongs to the account that added it** and nobody else sees it, until its **Shared** box is ticked — then it is everyone's. Redis credentials stay on the bridge; the browser is handed a placeholder, never the secret, and an edit that changes only settings keeps the stored one. Over plain http the account password crosses the network in the clear, so anything past a trial belongs behind an HTTPS reverse proxy — with a rate limit if the bridge is reachable from outside your own network. An **audit log** (`--audit-log`) keeps one JSON line per login and failed login, refusal, account change (registration, role, password, token, invitation), server-entry change, administrative command and confirmed command — and, opted in with `--audit-writes`, per data write; reads are never logged, passwords in arguments are blanked. `--audit-webhook` pushes the lines that need attention — failed logins, refusals, entry changes, administrative and confirmed commands, never a plain write — to a Feishu / Lark, DingTalk, WeCom or Slack group, signed where the bot checks, or as JSON to any URL. Behind an authenticating reverse proxy the bridge can take the signed-in identity from a header (`--trusted-header`), believed only on connections from the proxy's own addresses (`--trusted-proxy`) and only for names that are accounts — such an account is registered through the proxy with no password, and its role stays the bridge's. An account's server rules (`prod-*:ro`, …) say which shared entries it sees (by name glob or id), and where it is read-only.

### Read-Only Access for AI Assistants (MCP)
**Claude Code, Cursor or any MCP client can read your Redis through the bridge — as a read-only account, and only read.**

`POST /v1/mcp` is a Model Context Protocol server behind the same sign-in. The assistant signs in as an account that must be read-only — with a token of that account's (issued on its account page and shown once; it opens `/v1/mcp` and nothing else, is revoked on the same page, and names itself in the audit log), or like a script with HTTP Basic; a full account is refused whatever it asks, and the account's server rules decide which entries it sees. Ten tools are shaped for a model rather than a terminal — `list_servers`, `scan_keys` (paged, across every master of a cluster), `inspect_key` (type, TTL, memory, encoding, length and a preview), `server_info` and `slowlog` (parsed, per master), four diagnostic summaries — `slowlog_summary` (the slow log by command), `hotkeys` (a running `HOTKEYS` collection's report, Redis 8.6+), `memory_summary` (a bounded sample of keys, memory grouped by prefix) and `troubleshooting_report` (a single-shot diagnostic snapshot combining summary, `INFO`, `MEMORY DOCTOR`, `LATENCY DOCTOR`, `LATENCY LATEST`, redacted slow log and core settings) — and `read_command` for any other read. Every command goes through the page's read-only allowlist, and on top of it the tools refuse reads that return credentials (`CONFIG GET` of a password, `ACL LIST`) and the commands that would change or hold the connection every caller of that server shares (`SELECT` — the tools take a `db` instead — `MULTI`, blocking reads, `SUBSCRIBE`, …); scripts run only in their `_RO` forms. Replies are cut to fit a model's context, an account may make 120 calls a minute, and every call, reads included, is one line of the audit log. The self-hosting guide's [MCP section](./WEB.md#read-only-access-for-ai-assistants-mcp) has the one-line `claude mcp add`.

### What the Browser Leaves Out
**Nearly all of it: what is left out needs a file, a second window, or a connection to each node.**

The key tree, every value editor, the terminal, metrics with their 1h / 24h / 7d history, slow log, CONFIG, clients, memory analysis, value search, multi-database key search, cross-server compare (as a dialog, with *Copy to target*), server-to-server key copy, the troubleshooting report (saved as a download) and the recycle bin all work, and so do the streaming panels — `MONITOR`, Pub/Sub and keyspace events — whose connection the bridge holds while the page polls it; the bin and the history are kept on the bridge, the bin shared by everyone who sees the server. `MONITOR` is for full accounts, asks the lock's question on a locked entry, is audited and stops after ten minutes. Exports are downloads — keys with their values too, as JSON or CSV built in the tab (up to 64 MB, or copied straight to another server) — and imports are picked through the browser — a value, keys from a JSON or CSV export (up to 64 MB), a connection export, an RDB dump for the offline analysis — and the Protobuf viewers decode values there too, their schema pasted or chosen as a `.proto` file. A value written from the page is at most about 1.5 MB, one request to the bridge; a larger one opens read-only there and says why. Connection diagnostics and runaway script kills (`SCRIPT KILL` / `FUNCTION KILL`) run on the bridge, which is what dials the server for a page. An administrator's account page lists who is online and on which servers, and narrows the audit by server and by period. Left out: Topology and Sentinel administration, the script viewers, the Lua debugger, binary `.zedis-dump` key export and import, plus the shortcuts a browser keeps for itself (⌘N / ⌘T / ⌘W / ⌘Q). The value editors colour JSON and Lua with syntect there (the desktop's tree-sitter cannot be built for WebAssembly), folding blocks by their braces, and show a value over 512 kB plain. Tags, notes, favorites, recent keys, search history, saved scripts, Protobuf viewers and Settings are kept by the bridge, and the terminal's history by the browser, with credentials blanked: an account's own lists and preferences follow it to any browser, key tags and notes are a server's (left one key at a time, by an account that may write there), and a saved script is private unless shared, every save audited. A panel that is left out renders the same explanatory placeholder a missing server command gets, rather than failing. A page left in a background tab slows its own polling down. The desktop app remains the complete client.

## ⌨️ Productivity

### Workspace Tabs
**Multiple connections side by side — Cmd/Ctrl-click a server to open it in a new tab.**

Each tab keeps its own connection and view state (key tree expansion, scroll, selection survive tab switches). The tab strip appears only with two or more tabs (max 8): click (or **⌘1–8**) activates, middle-click or × closes, drag reorders, and right-click offers close / close-others / close-to-the-right. Background tabs relax their heartbeat to one refresh per 30 seconds, and the open-tab list is restored on the next launch with background tabs reconnecting lazily on first activation.

### Multi-Database Key Search
**⌘⇧F — find a key across many connections at once.**

An overlay that searches a key name across a chosen scope: every open tab's connection, one server group, or an explicit checkbox set of servers (with select-all; both the scope and the per-server scan limit are remembered). The cheap exact lookup runs first and shows instantly; if nothing matches exactly, a capped `SCAN` runs automatically — and when exact hits exist, the scan waits behind a button so the fast answer is never delayed. Clicking a hit jumps straight to that server, db, and key.

### Command Palette & Shortcuts
**⌘K fuzzy navigation, ⌘P recent keys, and a ⌘/ keyboard-shortcut reference.**

**⌘K** fuzzy-searches servers, panels, and the active connection's loaded keys (arrows to move, Enter to run, Esc to dismiss). **⌘P** is the quick-open for the current connection's recently opened keys — the Zed / VS Code gesture, available from tool pages too. **⌘/** opens a read-only, grouped overlay of every hotkey with per-platform symbols: ⌘N new key, ⌘S save, ⌘R reload the tree, ⌘⇧R reload the value, ⌘T set TTL, ⌘⌫ delete, ⌘E rename, ⌘F filter, ⌘J terminal, ⌘1–8 workspace tabs, Esc to step back. **⌘+ / ⌘− / ⌘0** zoom the whole UI (the same font size Settings drives). Every shortcut can be **remapped**: Settings → *Keyboard shortcuts* opens `keybindings.toml` in the config folder, one `id = "keystroke"` line per action, and the overlay shows your keys after a restart.

### Integrated CLI
**redis-cli terminal with completion, text / table / JSON replies, a multi-line Batch mode, and an AI command assistant.**

Version-aware command completion with inline argument/summary hints, each suggestion linking to its reference page on redis.io. Command history is kept **per server** and persisted locally: ↑/↓ walks it, and **Ctrl+R** opens an incremental reverse search over it. A pasted line keeps working when it still carries a leading `redis-cli`. The terminal runs on a **connection of its own**, so `SELECT`, `AUTH`, `CLIENT SETNAME` or `MULTI` typed there never touch the connection the key tree scans on — after a `SELECT` the prompt shows `[n]` while the terminal sits on a different db than the panel — and a blocking command (`BLPOP` / `BRPOP` / `BZPOPMIN`, `XREAD … BLOCK`, `WAIT`, …) is still refused up front rather than parking that connection. A one-click **Batch** mode swaps the REPL for a multi-line editor — one command per line, run with `⌘`/`Ctrl`+`Enter` (dangerous lines still route through the confirm dialog). Type **`? <question>`** to ask the configured AI endpoint for the matching command in plain language — the suggestion lands in the input box for review (never auto-executed, so the danger confirmation and the read-only lock apply unchanged), with a short explanation in your UI language. Only the question and server *metadata* (version, deployment, modules) are sent — never key values. Replies render as plain text, an aligned **table** (lists, hashes, `WITHSCORES` / `CONFIG GET` pairs) or pretty **JSON**, switched from the output toolbar and remembered across sessions; a `MULTI … EXEC` block is laid out as one grid of the queued commands beside their replies, and a Batch run ends with a commands / errors / elapsed summary. The output pane is selectable, with a right-click menu (Copy, Select All, Copy Output, Save Output…, Clear), and **Save** writes the transcript as a text file to Downloads. The AI endpoint needs only a base URL — a local model behind Ollama or LM Studio runs without an API key.

### Lua Script Library
**Save, reuse, and EVALSHA-run Lua scripts with hit-rate stats.**

A local library of named Lua scripts (source + precomputed SHA1) with starter templates, one-click **EVALSHA-first** execution (an `EVALSHA_RO` toggle on Redis 7.0+ makes the server refuse writes inside the script), saved `KEYS` / `ARGS` defaults for one-click re-runs, and lifetime hit/miss counters to spot scripts being flushed from Redis's cache — plus cache control (**Warm** = `SCRIPT LOAD` without executing, and a guarded `SCRIPT FLUSH`) and library import/export. (Distinct from **Functions** — that manages server-side `FUNCTION` libraries.) A **Kill script** button sends `SCRIPT KILL` (the Functions panel has **Kill function** for `FUNCTION KILL`) over a fresh connection that a `BUSY` server still answers — the regular one is stuck behind the script — and the status bar offers the same button whenever `BUSY` is why the link is down. Every data node is told (on a cluster any master may be the busy one); a script that has already written is reported as unkillable; Zedis does not shut the server down for you.

**Debug** steps through a saved script with the Redis Lua debugger (`SCRIPT DEBUG`): the source is drawn line by line, a click on a line number sets or clears a breakpoint, and **Step** / **Continue** / **Abort** drive the script while the side column shows the line it is paused on, its locals, the `redis.debug()` output and the Redis calls it made, and at the end its result or error. A paused script can be asked a Lua expression (in a call frame of its own: globals such as `KEYS` and `ARGV`, not the script's locals) or made to run a Redis command. By default the server forks and every change the script makes is rolled back when the session ends; **Keep changes (SYNC)** runs it in the server itself, keeping its writes and blocking every other client while it is paused, and asks first. Closing the debugger aborts a paused script. Desktop only, and not on a cluster (the session needs one connection to one node).

### First Launch & Onboarding
**A welcome card on the first run, one-time hints on the panels that need context.**

The first launch shows a three-step welcome card — add a server, browse decoded values, open the command palette. Panels with a learning curve (Topology, Memory Analyzer) show a one-time banner explaining what they sample and how to read the result. Every hint appears once and never comes back.

### Diagnostics & Recovery
**A one-click diagnostics bundle, crash reports, and a repair path for damaged local files.**

The title-bar menu's **Export Diagnostics** writes one zip to Downloads: a summary, your `zedis.toml` and `redis-servers.toml` with secrets redacted, the newest log files, and any crash reports — everything an issue needs, none of it collected by hand. If a session ends in a crash, the next launch surfaces a card pointing at the saved report and its stack trace. And if the config or the local database file is damaged, Zedis opens a recovery window offering **Back up & rebuild** instead of refusing to start. Logs roll to files under the config directory (**Open Logs Folder** in the same menu) and are pruned after ~3 months.

### Staying Current & System Integration
**An opt-out update check with a checksum-verified download, a system tray, and your own proxy.**

Zedis checks GitHub for a newer release on startup — at most once every two days, skippable per version, and switchable off entirely in Settings (there is also a manual **Check for Updates**). GitHub's release CDN is slow to unreachable from mainland China, so every request — the check, the manifest, the release notes and the download itself — falls back to the **[Gitee mirror](https://gitee.com/vicanso/zedis)**, which carries the same files copied from the same release. When a newer release is found, a chip appears in the title bar. Clicking it asks for the release again — the chip spins meanwhile — and opens a popover under it with what changed since the running version, **Skip this version** and **Update and restart**. The download verifies the asset's **SHA-256** against the release manifest before anything runs, whichever host served the bytes. On **macOS the install then completes in place** — the DMG mounts silently, the bundle identifier is verified, the new app is copied over the old one (which is parked in temp, never deleted under the running process) and Zedis **restarts into the new version** on its own; anything that blocks that path falls back to the classic drag window, and Zedis quits so it can finish. Windows hands the verified MSI to its installer and quits for the same reason, Linux hands the file to the desktop handler and keeps running. Progress shows in the popover, in place of its buttons, and as a percentage on the chip.

An **Include pre-releases** switch in Settings adds pre-release versions and the rolling **nightly** build to the check (on by default for a nightly build, which compares by build time, so a fresh nightly is offered as soon as it lands).

On macOS and Windows an optional **system tray** icon shows the active connection, its memory and OPS, and offers quick-connect to any configured server. All of the app's own outbound requests (update check + AI) follow the OS system proxy by default and honour an explicit **HTTP / SOCKS5 proxy** you set in Settings — or `none` to force a direct connection.

Zedis runs as **one instance per profile** (config directory): launching it again just brings the running window to the front, and a **`redis://` / `rediss://` link** — clicked in a browser or docs page, or passed on the command line — opens in it, landing on the saved connection with that host / port / TLS / user (or saving the link as a new one), in the link's `/db`. The schemes are registered by the macOS bundle, the Linux desktop entry and the Windows installer; a Settings button re-claims them on macOS when another client took over. macOS also gets the standard **Edit** and **Window** menus, the title bar is **tinted on PROD-tagged connections**, and a maximized window comes back maximized. Settings → *Date & Time* chooses the **time zone** (local or UTC) and the **date layout** used by every timestamp in the app, and *Local Data* **exports** tags, notes, favorites, script viewers, Lua scripts and proto bindings to a JSON file you choose — and **imports** such a file, merging it into this machine.
